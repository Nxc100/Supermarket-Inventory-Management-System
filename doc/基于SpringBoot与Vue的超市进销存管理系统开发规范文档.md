## 0 项目范围与技术栈约束

### 0.1 统一技术栈

以下均为实现约定，不新增业务能力。项目采用一个 SpringBoot 单体后端、一个 Vue 前端、一个本地 MySQL 项目库，按业务模块组织代码。

| 层面 | 统一选择 | 执行要求 |
| --- | --- | --- |
| Java | JDK 17 LTS，构建目标17 | 与当前开发机主版本一致；源码、IDE、Maven、运行JDK保持一致 |
| 后端框架 | SpringBoot 3.5.x，初始参考基线3.5.16 | 首次脚手架启动验证后在pom锁定精确版本；后续不能随功能开发自行切换到Boot2或Boot4 |
| 构建 | Maven 3.9.x + Maven Wrapper | 提交`mvnw`、`mvnw.cmd`和wrapper配置；统一通过wrapper构建 |
| Web与校验 | Spring MVC、Jakarta Validation | 使用`jakarta.*`校验，不混用`javax.validation.*` |
| 持久层 | MyBatis-Plus 3.5.x、必要的MyBatis XML | 采用`mybatis-plus-spring-boot3-starter`；复杂锁定、聚合和批量SQL写XML，不同时引入JPA |
| 安全 | Spring Security、其JWT编解码能力、BCrypt | 统一认证入口与方法授权；不手写JWT签名或密码摘要算法 |
| 数据库 | MySQL 8.0.34、InnoDB、utf8mb4 | 严格模式、北京时间、外键和CHECK；以唯一SQL的实际结构为准 |
| 前端 | Vue 3、TypeScript、Composition API、`script setup` | TS开启strict；不混入Vue2和另一套业务框架 |
| 前端构建 | Vite、npm、Node.js 24 LTS | 与现有Node24环境适配；首次验证后锁定Vite等精确版本；统一`package-lock.json`与`npm ci` |
| 路由与状态 | Vue Router、Pinia | 登录信息与权限集中管理；普通表单状态留在页面 |
| UI与图标 | Element Plus、配套图标 | 不混用Element UI、Ant Design等第二套组件库 |
| 请求与图表 | Axios、ECharts | 各一个统一封装；图表数据来自后端真实聚合 |
| 金额展示计算 | `decimal.js`等单一精确十进制工具 | 脚手架时确定并锁定一个；后端BigDecimal为最终权威 |
| 后端测试 | JUnit 5、Spring Boot Test、MockMvc | 真实MySQL验证持久化与并发，不用H2结果替代MySQL验证 |
| 前端测试 | Vitest、Vue Test Utils；关键闭环用Playwright | 只为关键逻辑和交互建立必要测试，避免镜像实现的低价值测试 |
| 格式与检查 | Java统一格式化；ESLint、Prettier、`vue-tsc` | 配置随仓库提交，同一模块不采用不同格式策略 |

SpringBoot 3.5.16官方要求至少Java17；MyBatis-Plus为Boot3提供独立starter。首次搭建须验证依赖组合，而不是逐个复制最新版依赖。[SpringBoot系统要求](https://docs.spring.io/spring-boot/3.5/system-requirements.html)、[MyBatis-Plus安装说明](https://baomidou.com/en/getting-started/install/)

Vite及UI依赖需按选定版本核对运行环境，再提交锁文件；不要把官方示例中的`latest`写入项目依赖。[Vite环境要求](https://vite.dev/guide/)、[Element Plus安装说明](https://element-plus.org/en-US/guide/installation.html)

### 0.2 范围限制

必须完整实现需求的三类角色与七大模块。单门店、单库存地点、基本整数单位、整单一次入库、模拟收款、受限纠错、人工审核、统计分析与智能建议是既定边界。

禁止自行增加多仓库、会员积分、完整财务、真实支付退款、完整退换货、自动下单、预测算法、连锁门店、供应商登录或公网运维要求。原文中的参考研究和后续展望不自动成为开发任务。

不默认引入Redis、消息队列、微服务、分布式事务、配置中心、搜索引擎、容器集群和复杂低代码平台。当前单体与MySQL能够解决的问题，应在该结构内解决。必要的新依赖必须说明用途、兼容性及其替代了什么重复实现。

### 0.3 版本与环境

- Maven依赖优先交由SpringBoot BOM管理；只有未管理的依赖单独锁版本，不能用覆盖传递依赖的方式随意拼版本。
- 前端只保留一种包管理器和一份锁文件，禁止同时提交yarn/pnpm锁文件；不在功能修复中顺带全量升级依赖。
- 第一次建立脚手架时记录JDK、Node、Maven、MySQL和主要依赖的实际版本到根`README.md`；以后以pom、锁文件和wrapper为准。
- 默认后端端口8080、前端5173、MySQL3306属于实现约定，可通过本地配置覆盖；不能写死开发者绝对目录。
- 后端使用`local`与`test`配置区分开发库和测试库；单元测试不需要数据库时不得强制加载外部服务。
- 本机回环连接兼容：后端监听地址沿用SERVER_ADDRESS配置；Vite可通过BACKEND_PROXY_TARGET指定相同的后端回环地址，缺省仍为http://127.0.0.1:8080。本机IPv4连接发生故障时可显式使用IPv6回环（SERVER_ADDRESS=::1、BACKEND_PROXY_TARGET=http://[::1]:8080）。代理配置仅在Vite进程读取，不进入前端包，不自动切换目标或重试业务写入。
- Vite后端代理使用两个独立的有界HTTP连接池：普通业务与建议接口各最多4条活动/4条空闲，LIFO，连接空闲上限25秒并预留服务端Keep-Alive安全余量。模型调用不占普通业务池；普通请求10秒/建议请求20秒的既有超时继续适用，不通过自动重试业务写来规避网络错误。调整连接策略须保留故障对照与取消/丢失响应回归结果，不能以短探针代替整站验收。
- JDBC会话状态统一经Spring/JDBC API管理，启用Connector/J的useLocalSessionState以避免每次写入前额外查询事务状态；不得直接用SQL改autocommit、事务只读或隔离级别后绕过驱动状态。服务端只读传播保持启用，不缓存业务行，不改变事务边界，不自动重试业务写。真实数据库回归须同时核实驱动和服务端的只读/隔离/自动提交状态及回滚，连接故障按原规则丢弃失效连接。参考[Connector/J会话状态选项](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-performance-extensions.html)。
- 本次制定规范不安装、升级JDK/Node、不启动或重置现有业务数据库。模型扩展依赖锁定markdown-it15.0.3、DOMPurify3.4.17及@types/markdown-it14.1.2，未升级既有框架。

## 1 界面设计与交互规范

### 1.1 视觉与布局

- 采用清晰、克制、易读的业务管理风格。主题色、状态色、字体层级、圆角、间距、表格行高使用CSS变量集中维护，映射到Element Plus主题变量。
- 默认浅色主题即可。页面突出业务状态、库存数量、单据金额和待处理任务，避免装饰占用操作空间，不引入与业务无关的动画背景。
- 状态同时展示文字和颜色，如“待审核”“已驳回”“盘点冻结”，不能只显示彩色圆点。
- 采用左侧导航、顶部工具栏和主内容区；顶部显示当前用户姓名、角色、头像、个人中心、退出登录。
- 管理员工作台展示全店指标和待审核任务；采购展示本人采购、预警和盘点；收银突出快速开单、本人销售和只读库存。
- 常规内容区采用统一页标题、查询区、操作区、表格、分页；采购、销售、盘点的金额汇总和主要动作保持可见，减少无必要跳转。
- 适配常见笔记本桌面分辨率。长表允许横向滚动，关键标识列和操作列按需固定；不能依赖固定宽高导致按钮、明细或弹窗被裁切。
- 默认正文14px、标题18～24px、间距采用4/8px倍数作为实现约定；模块不得另建一套零散视觉尺度。

### 1.2 表单、列表与状态

1. 必填项标星，前端即时校验改善体验，后端独立复核。校验失败保留已填内容并定位字段/行号，不只弹“请求失败”。
2. 空、0、未填分别处理：未填实盘是`null`，实盘0为有效输入；条码无值提交`null`；不能用`value || default`覆盖合法0。
3. 列表统一查询、重置、分页、默认倒序、加载、空态、错误重试；筛选变化回第一页，删除末页最后一行后修正页码。
4. 日期区间、图表指标、查询汇总的范围须可见；收银全店聚合和本人销售明细不能假装是同一范围。
5. 用户无权限的动作不显示；有权限但状态不允许的动作禁用并解释原因。后端仍需重新校验，不能依赖按钮是否可见。
6. 草稿保存、审核通过、关闭、撤销、纠错等采用准确动作名，不把所有业务按钮都叫“保存”。
7. 详情页区分当前档案与单据历史快照，不能用主档实时价格、分类覆盖历史信息。
8. 加载状态按区域设置，统计或AI故障不遮住整站，旧筛选结果不能冒充新结果。
9. 颜色、图标、文案通过共享枚举映射输出。状态字典只有一份，不在每个页面重复编写。

### 1.3 交互反馈与确认

禁止业务代码使用浏览器`alert()`、`confirm()`、`prompt()`。统一反馈优先级：

1. 页面内即时更新：采购审核、销售完成、盘点完成后更新相关状态、列表、余额和统计卡片。
2. `ElMessage`：保存、操作成功及轻量失败提示，通常3秒；同一错误只能由请求层或页面的一方提示，不能重复弹两次。
3. `ElMessageBox`：删除草稿、停用账号、采购审核、撤销入库、销售纠错、盘点关闭等风险动作二次确认，明确单号和数量/金额影响；驳回、关闭、纠错等必要原因要校验后再提交。
4. `ElNotification`：仅用于确有必要的全局通知，不作为每次保存的默认反馈。

普通离开表单使用统一组件或路由守卫；浏览器关闭/刷新无法自定义UI时，可使用标准`beforeunload`事件保护未保存内容。这是浏览器能力适配，不允许通过业务代码调用原生弹窗。

### 1.4 请求、重复点击与结果未知

- 提交期间按钮禁用并显示加载，异步过程使用`try/finally`恢复状态；未收到服务端成功不能先清空表单、购物内容或先提示成功。
- 搜索框可防抖，旧查询通过AbortController或请求序号取消/忽略，避免慢响应覆盖新筛选结果。
- 采购审核与盘点审核发生状态冲突时刷新详情并说明“已被处理”，不能自行改成成功状态。
- 销售网络超时区分“明确失败”和“结果未知”：结果未知时保留原请求键和原提交快照，查询原结果或用相同内容、同键重试；不能自动换键再结算。
- 请求内容经用户明确修改后才建立新提交键；未决原请求须先核实结果，防止同时保留两个可能成交的请求。
- 未保存离开提示、服务端校验失败提示、超时结果恢复分别处理，不能用一个清空页面函数代替。

### 1.5 表格、数字和图表

金额右对齐并显示两位小数，数量附基本单位；0显示为0，未知显示“未填/暂无”，不以横线掩盖真实零值。ID和条码不做数字四舍五入或科学计数。

ECharts通过共享容器处理尺寸变化、加载、空态和销毁；路由离开时释放监听与实例。图表必须有对应可读明细、指标单位、时间和统计范围；库存饼图说明是基本单位数量占比。空数据不画假饼图，不硬编码柱状图数值。

## 2 功能开发前置规则

### 2.1 必读文件

开始任何功能、修复或重构前，按顺序读取：

1. `doc/超市进销存管理系统功能需求文档.md`相关章节及其引用的统一规则，唯一权威业务需求。
2. `doc/数据库/supermarket_inventory.sql`，唯一可信数据库基准，含表结构、视图、约束和初始数据。
3. 本规范，明确技术栈、目录、权限、事务、接口及测试约束。
4. 当前功能涉及的Entity、DTO、VO、Enum、Mapper、Service、前端API、类型、路由及已有测试；文件尚未建立时先设计最小必要部分。
5. 涉及库存或统计时额外阅读需求第9章、A12统计口径及现有库存内核；涉及图片或AI时阅读相应安全与降级要求。

数据库设计说明和`03_verify.sql`、`04_queries.sql`仅帮助理解和验证，不能优先于唯一需求或唯一初始化SQL。

### 2.2 开发前最小分析

在开始编码前明确：需求编号、允许角色、本人/全部范围、操作入口、输入输出、合法状态转换、涉及表/字段、事务边界、异常及关联回归。简单任务可写在工作记录或变更描述中，不为每个按钮新建说明文档。

发现不一致时：业务行为由需求裁决；数据库结构由唯一SQL确认；技术实现由本规范约束。SQL缺少支撑需求的字段时同步补充SQL，不能删减需求来迁就旧表；规范与需求冲突时修正规范，不能悄悄改变业务。

### 2.3 开发顺序

按需求14.1推进：基础认证和档案 → 采购与库存内核 → 销售 → 盘点预警 → 统计 → 智能建议 → 完整闭环。跨步骤允许迭代，但不能以“后续再做”为由宣布七大模块整体完成。

每次采用一条纵向流程：契约与校验 → Mapper/Service → 接口 → 页面 → 权限和异常 → 测试 → 文档。共享组件、认证、请求层、枚举、库存内核优先复用，不能复制一整套再修改。

### 3.2 模块内分层

每个需要持久化的模块按实际需要设置`controller`、`dto`、`vo`、`entity`、`enums`、`mapper`、`service`。不要为一个简单只读接口强建空目录、接口和Impl配对；只有多实现、外部适配或清晰边界确有需要时提取接口。

| 层 | 责任 | 禁止 |
| --- | --- | --- |
| Controller | 接收DTO、校验、取得当前用户、调用业务服务、输出VO | 写业务事务、计算余额、拼SQL、直接返回Entity |
| DTO/Query | 操作输入与查询条件，字段白名单和校验 | 接受客户端任意审核人、归属人、库存、状态、权限 |
| Service | 权限范围、状态、金额、事务、编排、审计 | 吞异常后返回成功；通过Controller调用另一模块 |
| Mapper/XML | 参数化SQL、行锁、分页、批量、聚合 | 决定前端角色；直接读登录请求；拼接用户输入SQL |
| Entity | 数据库存储映射 | 兼任请求对象、响应对象或前端表单 |
| VO | 当前角色允许的展示字段 | 把完整实体转Map后仅在前端隐藏敏感数据 |
| Adapter/Client | 文件或大模型等外部能力 | 控制库存、业务状态或用户权限 |

### 3.3 依赖与库存写入所有权

业务依赖保持单向：Controller → 业务Service → Mapper/领域组件；采购、销售、盘点的命令服务统一调用库存内核。统计只读查询，AI只调用摘要构建器和模型适配器，不反向驱动采购或库存写操作。

合并表按字段划分写入所有权：

- 商品档案服务只改`product`的档案、售价、阈值和开关；不能用通用更新写`stock_qty`、冻结指针和库存版本。
- 采购草稿服务维护未生效`purchase_item`的采购/到货字段；入库后快照和来源只读。
- 库存内核唯一负责`product.stock_qty`、`purchase_item.stock_qty`、冻结指针、库存版本和`stock_movement`写入；首次入库批次建立与业务审核处于同一事务。
- 采购核对服务仅维护当前核对字段与历史，不写原采购金额、实收量和库存。
- 销售和盘点服务拥有其单据状态、明细与原因；库存内核不得调用这些Service形成循环依赖。

库存内核可用专门Mapper访问上述库存列，不为避免“跨表访问”反而分散库存写入。纯CRUD生成代码只能用于安全的档案操作，禁止直接暴露`IService.updateById`等通用库存或状态更新接口。

## 4 后端代码质量约束

### 4.1 命名与类型

- Java类`PascalCase`，方法/字段`camelCase`，常量`UPPER_SNAKE_CASE`；包名全小写。SQL表列遵循现有`snake_case`。
- 请求对象按用途命名，如`PurchaseCreateRequest`、`PurchaseReviewRequest`、`SaleCompleteRequest`，禁止一个包含所有字段的万能DTO。
- 查询与响应区分，如`PurchasePageQuery`、`PurchaseDetailVO`、`CashierInventoryVO`；不能让收银响应继承带成本的管理员VO。
- 使用枚举集中表示角色、状态、原因、支付方式和流水类型，编码与唯一SQL一致；禁止散落`"PENDING"`或无解释数字。
- 金额用BigDecimal，数量与ID用适当整型；日期用LocalDate，业务时间使用统一Clock和北京时间转换。禁止`double`计算交易金额、禁止以`new Date()`散落决定业务日。
- 对`null`和0使用显式判断；对集合和分页边界做参数校验，拒绝未知枚举、空明细、重复非法行。

### 4.2 实现方式

采用构造器注入，依赖显式、字段尽量`final`；不使用静态Service容器或在工具类中查Spring Bean。转换逻辑用显式方法或既定映射工具，不用无白名单反射复制把用户输入覆盖到持久化实体。

Controller保持简短，Service按“校验—加载/锁定—状态判断—业务计算—写入—审计—返回”组织。复杂批次分配可提取为可单测的纯组件，但不为每个算式建立策略工厂。长方法、多重嵌套或同一规则被复制时优先拆清职责，不以任意行数达标代替可读性。

公开服务、跨模块方法和关键事务说明输入约束、状态、权限、锁序与失败影响。注释解释为什么保留反向事件、为什么冻结不归零等业务原因，不重复翻译代码。禁止长期保留大段注释代码、废弃接口或无工单对应的核心`TODO`。

### 4.3 异常与日志

使用统一业务异常、错误码和`RestControllerAdvice`；Spring Security认证失败及拒绝访问也返回相同错误结构。保留异常链供日志定位，不把SQL、堆栈、文件绝对路径或外部服务原始错误直接返回页面。

日志使用参数化SLF4J，至少携带`traceId`、动作、对象和结果；不记录密码、JWT、密钥、完整手机号或无关模型输入。库存等成功审计与业务事务一起提交；失败请求的日志不能因主事务回滚而误记为成功，可写应用日志，确需落失败审计时使用明确的独立短事务。

禁止捕获`Exception`后返回`true`、空列表或成功响应，禁止忽略Mapper影响行数，禁止通过关闭校验、移除外键或跳过测试掩盖错误。

## 5 接口与数据契约

### 5.1 路径与操作

实现约定：统一业务前缀`/api/v1`，资源路径使用英文复数名及短横线；查询GET、新建POST、部分编辑PATCH、允许删除DELETE。审核、驳回、提交、撤回、关闭、纠错等显式动作使用POST子路径，不使用一个PATCH任意改状态。

例如`POST /api/v1/purchases/{id}/approve`是命名示例，**不是已存在接口**；首次实现时将最终路径、权限、DTO/VO、异常和用例写入需求A06对应章节。路由调整必须同步后端注解、前端API和测试，不长期保留两份等价接口。

### 5.2 响应与HTTP语义

实现约定：JSON统一封装，字段为`code`、`message`、`data`、`traceId`；成功`code="OK"`。列表`data`固定含`records`、`total`、`pageNum`、`pageSize`。文件二进制响应不套JSON壳。

```json
{
  "code": "STATE_CONFLICT",
  "message": "该采购单已被处理，请刷新后查看",
  "data": { "currentStatus": "IN_STOCK" },
  "traceId": "请求追踪标识"
}
```

| HTTP状态 | 用途 | 处理 |
| --- | --- | --- |
| 200/201 | 查询/操作成功、新资源创建 | 返回实际已提交结果 |
| 400 | 参数、字段、格式校验失败 | 可带安全的字段/明细行错误 |
| 401 | 未登录、过期、凭证版本失效 | 一次提示后清登录态，阻止重复跳转 |
| 403 | 已登录但缺功能权限 | 页面提示无权操作，不伪装成功 |
| 404 | 对象不存在或无权枚举的他人私有对象 | 同类接口采用一致策略，避免泄露对象存在性 |
| 409 | 状态冲突、库存不足、价格变化、重复键内容冲突 | 返回可修正信息，保留当前表单 |
| 500 | 未预期内部错误 | 安全提示及traceId，记录内部原因 |
| 503/504 | 智能服务不可用/超时 | 只降级建议区域，基础业务仍可用 |

业务错误不统一包在HTTP200；前端不能只判断HTTP200而忽略业务码。错误信息不得包含本角色无权查看的成本、他人销售明细或供应商联系人。

### 5.3 序列化与校验

- BIGINT ID统一为十进制字符串，前端类型`Id=string`，避免JavaScript整数精度损失；不可对ID、条码做`Number()`。
- 金额请求响应统一为两位小数字符串，例如`"60.00"`；前端精确计算仅用于展示，后端重算最终值。数量上限按需求及SQL处理，禁止小数数量。
- 日期使用`yyyy-MM-dd`；时间使用带`+08:00`的ISO格式，统一序列化器负责数据库LocalDateTime与接口时间的转换。
- 日期区间前端可展示含首末日，后端转换为`[开始日00:00, 结束次日00:00)`；不得将日期字符串转UTC后偏移一天。
- Bean Validation处理格式，Service处理角色/状态/跨字段关系，数据库约束最后兜底。生成列、合计、经办人、审核人、业务时间均由服务端决定。
- 创建/更新DTO字段白名单明确；安全或库存命令中出现伪造角色、审核人、库存字段时拒绝，不允许自动绑定到Entity。
- 排序字段映射固定白名单，分页默认10、允许10/20/50；不得把客户端字段原样拼入ORDER BY。

### 5.4 契约唯一性

后端OpenAPI注解与真实DTO/VO同步；前端`api/<module>.ts`集中定义调用，`types`集中定义契约，页面不拼URL、不散写Axios。可采用一次确定的类型生成方案，但不要求为毕设搭建独立接口平台。

接口未实现时可短期Mock做页面开发，必须标注并可关闭。生产业务路径不得默默回退到Mock成功，联调验收必须接真实服务和真实业务数据。

## 6 认证、授权与数据范围

### 6.1 统一认证

实现约定：使用Spring Security认证链和签名JWT，前端以`Authorization: Bearer`发送；签名密钥由后端环境/本地配置提供，不能写死在前端或仓库。Token有效期默认2小时、可配置，不引入刷新Token系统；过期重新登录。

JWT包含用户标识、用户凭证版本、角色权限版本、签发/过期信息；每次请求加载当前账号与角色并比较版本及启用状态，不能只信Token中旧角色。改密、重置、停用、角色变更和退出按约定递增凭证版本；授权变更递增角色版本。退出采用该用户全部会话失效的轻量方案，明确为实现约定。

前端Token只通过一个认证Store和请求拦截器使用，采用Pinia与sessionStorage保持当前标签页刷新；禁止写入URL、日志和页面展示。业务接口不以Cookie作为隐式认证来源；后端安全配置据此明确CSRF策略，不能用`permitAll`解决401或跨域问题。

### 6.2 功能、归属和字段三层校验

1. 功能权限：统一权限代码来自SQL现有权限目录；Controller/方法授权与业务Service校验配合，不能只检查角色名称或前端菜单。
2. 数据归属：采购/盘点看本人，收银销售看本人，管理员看全部；详情、修改、审核关联、结果查询和历史接口都检查，不能只在列表加条件。
3. 字段投影：收银库存不返回成本、来源采购和供应商；AI类型和摘要同样授权。禁止完整JSON返回后用CSS或`v-if`隐藏敏感字段。
4. 全店销售图表权限不扩大本人销售单明细权限；采购能使用库存摘要所需的聚合销量，不因此开放销售记录或销售分析页。
5. 供应商共享和库存共享不改变采购单归属。库存来源单号可见不意味着来源单详情可读。

### 6.3 账号与管理员保护

密码使用BCrypt校验，不返回摘要，不打印旧密码。权限修改只允许在岗位上限内勾选，不能修改第四种角色或把采购/收银升为审核岗位。

最后管理员检查需同事务、统一锁定ADMIN角色行后检查启用管理员数量及关键权限，避免并发同时移除最后两个管理员。账号停用/改角色前处理本人未完成采购与活动盘点，不能留无法接续的冻结。请求已通过授权并进入事务后是否允许完成采用一致实现；不能依赖已撤销的前端缓存发起后续命令。

### 6.4 前端权限与会话切换

路由守卫加载当前用户和菜单；按钮用统一权限指令/组合函数，业务状态另行判断。退出、401、用户切换清理所有权限、页面缓存、购物内容、预览图和本人查询数据；旧账号未结束请求返回时按会话序号丢弃结果，不能覆盖新账号页面。

开发用Vite代理访问同源`/api`，后端按实际开发来源配置必要CORS；禁止为图省事允许任意来源携带凭证。

## 7 数据库与SQL维护

### 7.1 唯一基准

只以`doc/数据库/supermarket_inventory.sql`为全量结构与初始数据基准。已有`01_schema.sql`、`02_seed.sql`为历史分离脚本，不再作为开发初始化入口；其他临时合并文件不能成为第二套基准。校验/查询脚本不是结构权威。

现有权威文件为Navicat全量导出，包含`DROP TABLE/VIEW`、临时关闭外键和固定日期的样例数据，未自行创建/选择项目库。**只在明确选定的空库或可重置测试副本导入，禁止每次启动自动执行，也禁止在正在使用的库中重新导入。** 本规范不执行该文件，不重置现有数据。

新副本导入要检查外键、CHECK、生成列、视图依赖顺序、SQL模式和最终校验结果；不能把“脚本跑到最后”当成全部对象成功，也不能通过永久关闭外键绕过问题。当前种子的日期是2026-11-10快照，测试边界须控制Clock/测试日期或在隔离副本更新基准，不能假定永远临期。

### 7.2 结构变更

1. 先核对需求，再以最小改动设计字段/索引；沿用16张表的既有合并关系，不随意拆表，也不为减少表数牺牲约束和可查询性。
2. 同步更新唯一SQL中的DDL、索引、约束、相关视图和INSERT列值；新增字段注意现有导出是否为无列名INSERT，避免错位。
3. 不用ORM自动建表/自动改表，不在启动脚本塞ALTER，不保留临时`fix.sql`、`new_init.sql`等平行基准。
4. 若已有数据库需升级，在需求对应维护记录写明增量步骤、数据处理和兼容范围，以受控执行应用到既有库；全量SQL仍描述最终新库形态。初始文件不是增量迁移脚本。
5. 本地已有业务数据时先评估影响并备份必要数据，禁止为了开发方便直接删库。新旧接口兼容期保持字段可读；字段删除/改名先迁移调用方和数据再移除。
6. 新空库验证和既有数据验证都需覆盖；变更后更新`03_verify.sql`和受影响数据库测试，不能降低校验标准使其通过。

### 7.3 Mapper与查询

- 显式字段投影，不在面向接口的查询中`SELECT *`；关联与归属条件在SQL落实，防止先取全量数据再在Java内筛选。
- MyBatis参数使用`#{}`；动态列名通过服务端白名单选择，禁止`${用户输入}`。
- 分页不能先查全表；批量明细用批量查询/批量写入，避免每条商品发一次查询形成N+1。
- 以实际查询与执行计划决定索引，不为每列都建索引；不能删除已有索引而不检查列表、流水、统计和锁范围。
- 生成列由数据库生成，INSERT/UPDATE不能把`line_amount`、`change_amount`、差异生成列当普通可写字段。
- JSON采用固定格式、类型处理器和具体对象，不在多个模块各自拼字符串；审计JSON不参与库存扣减和交易金额计算。
- 未引用档案与从未提交草稿按需求删除；有业务引用不能启用全局逻辑删除插件掩盖FK，也不能级联抹掉历史。

## 8 事务、并发、库存与幂等

### 8.1 事务边界

采购审核入库、入库撤销、销售确认、销售纠错、盘点开始/审核/关闭、核对版本保存均由公开业务命令Service开启明确事务。库存内核参与同一事务，不另开`REQUIRES_NEW`提交余额或流水，可用`MANDATORY`防止脱离事务调用。

使用Spring代理能拦截的调用路径，不能靠同类自调用触发`@Transactional`。业务失败或持久化失败必须抛出并回滚；受检异常的回滚策略须明确，不能catch后继续提交。邮件、远程模型、图片解码等慢IO不进入库存事务。

同一事务成功才返回业务成功，单据、明细、批次、商品余额、流水和成功审计同时生效或同时失败。HTTP连接超时不代表事务必然没提交，销售须按原键查结果。

### 8.2 统一锁序

已存在的目标单据先锁定，随后按`product.id`升序锁全部相关商品，再按批次ID升序锁`purchase_item`；禁止不同命令反向锁定。开始新盘点先锁商品并检查冻结，再建立新任务和快照，不反向锁其他模块的单据。

锁定库存行使用明确的单表`SELECT ... FOR UPDATE`，避免带多表JOIN的锁定语句意外扩大到来源采购单造成反向锁。先获得商品锁，再重新查询当前有效批次、商品价格、日期和冻结；不得拿事务外的库存数继续扣库。

建议库存事务采用READ COMMITTED并配合上述显式行锁，作为实现约定；初始化或测试先验证真实MySQL行为，不靠修改隔离级别替代行锁。冻结开始与库存写操作竞争同一商品行，先完成者决定快照包含哪些业务。

死锁或锁超时需回滚并给出可重试冲突。默认不自动重试写请求；只有已设计幂等且内容不变的命令可在完整新事务内有限重试，不能无限重试或在失效事务中继续SQL。

本地连接设置使用会话级wait_timeout=120、innodb_lock_wait_timeout=10，JDBC连接5秒、读取15秒并保活，避免失联测试会话长时间持锁；不改MySQL全局变量。接口集成测试与UI按顺序执行。写入结果未知仍须按业务幂等规则核实，连接设置不能代替结果查询，也不代表所有本机偶发网络问题已定位。

### 8.3 库存不变量

- 商品账面余额 = 有效批次余额之和 = 商品全部正反流水累计变化；批次也满足自己的流水累计。
- 批次余额不为负；条件扣减并检查影响行数，不能“查够了”后无条件更新。
- 冻结仅阻止交易，不把可售数归零；日期过期只改变可售资格，不自动无流水清空账面。
- FEFO/FIFO和原分配恢复遵循需求；不能把销售纠错恢复到任意新批次。
- 整单内任一商品失败全单回滚，不出现部分扣减；无差异盘点不写零变化流水。
- 保存/提交采购不入库，审核通过才入库；核对不修改原采购和库存，盘亏不制造销售收入。
- 已生效快照、来源和原金额不可覆盖；纠错生成反向事件。采购是否有后续业务必须查询流水历史，不能只看当前数量相等。

### 8.4 销售幂等

`sale_order.request_key`是一次确认的稳定业务键，`request_hash`是规范化输入摘要，`uk_sale_request`与流水唯一来源共同防重。摘要按稳定商品排序和明确字段计算，包含影响结果的数量、用户看到的价格、收款方式/金额，排除traceId、Token等非业务值。

重复键相同内容返回原结果；相同键不同收银员或不同内容拒绝。唯一键冲突导致事务回滚后，必须退出失败事务，再用新的只读查询读取已提交原单；不能在已标记回滚的事务里继续返回“查询成功”。

审核、关闭、撤回、纠错和盘点处理按单据锁、预期状态及唯一流水来源防重，不能仅靠前端按钮。状态重复处理时返回原结果还是409应在该接口契约固定，不可各次随机处理。

## 9 前端代码与共享能力

### 9.1 页面与组件

页面负责业务交互编排，组合函数承载可复用的列表/表单状态，API文件负责契约调用，纯工具函数负责金额、时间和路径。不要把API请求、权限、状态计算全部塞入一个几千行页面。

只被一个页面使用的组件就近放置；出现两个以上真实重复场景再抽象通用组件。共享表格不能做成难以调试的低代码平台；业务按钮、权限和特殊校验仍显式可读。避免过深props传递、随意全局事件总线和所有状态都塞Pinia。

禁止滥用`any`、`@ts-ignore`、非空断言掩盖数据缺失；第三方未知数据先校验并收窄类型。依赖数组/对象变动时清楚使用computed、watch和生命周期，不为缓存展示值维护多份可变副本。

### 9.2 请求层

一个Axios实例统一baseURL、Token、traceId、错误解析和401处理；AI请求允许单独配置超过后端模型上限的HTTP等待时间，不能因此增大全站结算超时。

当前建议请求Axios20秒，Vite建议路径代理20秒、客户端22秒；匹配项置于通用/api之前。通用接口保留原代理10秒和Axios12秒，避免模型15秒等待被通用代理提前截断。

本地Vite代理按0.3节的普通业务/AI独立有界连接池复用完整响应后的连接，异常或取消的连接由Node销毁；空闲25秒，活动请求仍由各路径proxyTimeout控制，不自动重试业务写。分页读取期间保留已知总数边界并禁用分页控件，失败后同步清零并回到第一页，避免控件因临时0总数自动吞掉第二页请求。

组件和全局错误处理约定谁负责提示，取消请求不弹失败；401仅触发一次会话清理，403不循环重登。禁止默认重试POST/PATCH/DELETE，GET重试也应有限且不覆盖用户新筛选。

API函数返回强类型`data`，是否解包在一处规定；页面不同时存在`response.data`、`response.data.data`两套使用方式。静态资源URL通过统一解析函数生成，禁止各页面写开发机地址。

### 9.3 状态变化后的刷新

成功写入后按影响范围刷新：采购审核影响采购、批次、库存、预警与相关工作台；销售影响本人记录、库存和销售统计；盘点完成影响任务、库存、流水与预警。只刷新当前可见或下次进入必取新的数据，不要求所有隐藏页面同时发请求。

采用明确的刷新函数或轻量失效标记，不能通过整页`location.reload()`掩盖状态管理问题。列表详情共存时同步更新，错误时不保留虚假的乐观成功；乐观更新仅用于可安全撤回的普通体验，不用于库存交易。

### 9.4 模型扩展实现约定（2026-11-11）

模型流式采用POST SSE及fetch ReadableStream，复用会话过期与版本隔离，禁止在URL放Token。服务端独立有界执行器、真实增量转发，远程读取总时限仍为既有模型超时；连接结束不等于调用未提交，浏览器断开后服务端有界收尾供同键查询。SSE仅在首个认证请求授权后启动，异步dispatch不得重新误判成未登录。

管理员模型配置沿用system.config/system.config.save及ADMIN服务端双重校验。Key加密存sys_config，AES-256-GCM主密钥由AI_CONFIG_MASTER_KEY或后端私有文件提供，不随JWT密钥变化、不写入SQL/前端/日志。模型名单、默认值和配置版本独立校验；进行中的调用使用取得的配置快照。ai_suggestion以可空字段保存服务商usage，NULL代表未知；原历史不补造Token。配置审计只保存无密钥的VO。

Markdown解析与清洗使用锁定版本的markdown-it（禁原始HTML）及DOMPurify白名单；实时及历史共用渲染组件，测试脚本/危险链接、表格溢出及流式未完成状态。依据[阿里云流式协议](https://help.aliyun.com/en/model-studio/stream)使用stream=true、stream_options.include_usage=true，处理delta.content、独立usage块及[DONE]，不将服务商错误正文透传。

## 10 图片、头像与本地资源

严格遵循G04和A04：前端选择单图、校验、预览、确认上传、取消；后端重新验证真实图片内容、大小、尺寸和允许格式。SVG、伪装图片、路径穿越和非图片内容拒绝，扩展名及浏览器MIME不能代替解码。

文件目录通过配置指定，数据库仅存相对路径。实际文件使用系统生成文件名，不用用户输入拼接路径；服务端将相对路径解析到固定根目录后验证未越界。日志不暴露本地绝对路径。

图片先写临时文件并完成校验，再以短事务绑定新路径；绑定失败清理本次孤立文件，旧绑定保持。替换/移除成功后确认用户头像及商品图片都无引用才回收旧文件，共用`测试图片.jpg`不得随意删除。不要让文件系统副作用假装可以被数据库事务自动回滚。

头像接口根据当前用户确定操作对象，不能接受任意用户ID；当前姓名、角色等受保护字段同样白名单。资源展示失败用默认图，不影响基础交易。测试图片缺失时显示占位，不能提交一个零字节JPG冒充真实样例。

## 11 统计与智能建议实现

### 11.1 统计

统一使用既有事件与库存视图或等价、经过对账的聚合查询。月度12个月补0，销售按完成正事件和纠错负事件筛各自时间；一商品分多个批次不能重复统计销售额。

库存饼图用账面数，低库存用可售量，临期/过期按批次，滞销与观察不足按需求A12。商品现价不重算历史，停用库存不凭空消失。查询筛选和下钻使用同一时区、区间和数据授权。

禁止为图表预置假数据、在前端重新实现与后端不同的统计口径，或在查询失败时悄悄换成演示图。统计查询不长时间持有库存排他锁，不作为销售事务的一部分。

### 11.2 AI适配与隔离

模型调用封装在单一适配接口，如`SuggestionClient`；只输入经过权限和字段过滤的聚合摘要，业务Service先验证建议类型。采购只能库存类，收银无任何建议，管理员全部；历史、详情、失败记录和输入摘要都执行同样授权。

库存或销售事务绝不调用外部模型。先取一致的业务摘要并记录采集时间，释放数据库事务/锁后发请求，再以短事务保存结果。配置缺失时基础应用仍可启动，不将API密钥缺失做成整个系统启动失败条件。

网络、认证、限流、超时、空正文、解析失败均转明确失败记录与可读提示；单次调用按需求默认上限15秒，连接/读取设置在适配层，前端等待略大于该总上限。不无限重试，不用全局弹窗阻断进销存。

固定测试输出必须标记`is_fixture=1`与测试来源，真实调用成功才保存真实结果；展示历史明确时间。模型正文当文本渲染，不执行其中HTML、脚本、SQL或“自动采购”指令。模型提供方不能直接访问库存Mapper或执行命令。

## 12 测试与回归保护

### 12.1 测试层次

| 类型 | 必须重点验证 | 不可替代项 |
| --- | --- | --- |
| 纯逻辑单元测试 | 金额、批次分配、状态判断、时间边界、请求摘要、权限集合 | 不能代替真实SQL与并发事务 |
| MySQL集成测试 | 唯一/FK/CHECK、生成列、行锁、余额/流水、整单回滚、对账历史 | H2或Mock Mapper不能证明MySQL正确 |
| 接口测试 | 三角色、本人范围、字段投影、伪造参数、状态冲突、幂等结果 | 只测页面菜单不能证明授权 |
| 前端交互测试 | 字段校验、空/0、加载恢复、二次确认、失败保留、旧响应隔离 | 只截图不能证明提交行为 |
| 闭环联调 | 需求13章场景与13.1完整脚本、AI失败下基础交易 | 数据库58项通过不能证明整站完成 |

新增或修复重要业务逻辑，先补可复现失败场景，再验证修改；仅文案、格式和低影响样式调整不机械编写镜像测试，按影响做人工/结构检查即可。测试断言最终单据、库存、流水、金额和权限，不能只断言HTTP200。

### 12.2 必须保留的高风险用例

- 库存5，两收银分别买4，最终最多一单成功；批次及总量非负。
- 一个请求双击、网络重试、同键不同内容，验证只生效一次或正确拒绝。
- 多商品中一项失败，所有库存、销售、流水和成功审计一起回滚。
- 采购审核与撤回、盘点审核与关闭竞争，只有一个合法状态转换成功。
- 盘点冻结与采购/销售同时竞争同一商品；驳回保持冻结、关闭/完成释放，无永久冻结。
- 未填实盘与0、盘盈/盘亏/无差异，原因校验和零流水规则正确。
- 到期当天、次日、阈值0、过期有账面、过期清理；不通过修改系统时钟测试。
- 修改售价/档案后历史快照不变，销售纠错原分配恢复，正负事件金额不重复。
- 三角色越权访问、本人ID替换、图表下钻、AI历史类型与敏感字段投影。
- 模型断网/超时/未配置与头像上传失败同时发生时，采购销售仍可用。

### 12.3 测试数据与隔离

默认使用独立`*_test`或`*_dbcheck`库，先明确目标再导入；自动测试不得重置开发者正在使用的项目库。使用固定Clock和明确数据准备控制日期，禁止写入本机全局时间或依赖“今天刚好是样例日期”。

集成测试创建自己的数据并回滚或按自身唯一标识清理，不依赖测试执行顺序；并发测试使用独立连接和可控同步屏障，不靠长时间sleep猜顺序。验收数据与性能数据分开，不能把少量功能样本包装成已通过大规模性能测试。

### 12.4 变更影响与最小回归

| 改动 | 最低回归范围 |
| --- | --- |
| 认证、权限、序列化、请求拦截器 | 三角色登录/失效、本人详情、敏感字段、至少一条交易和错误反馈 |
| 商品/供应商/分类 | 档案唯一/引用、采购选品、销售检索、历史快照、相关预警 |
| 库存内核、批次或事务 | 采购、销售、纠错、盘点、预警、库存一致性及并发高风险用例 |
| 销售金额或状态 | 收款找零、幂等、跨批次、整单回滚、纠错、销售图表 |
| SQL字段、索引或视图 | 新库导入、既有数据兼容、相关Mapper、28项一致性及受影响约束测试 |

| 共用前端组件或主题 | 至少一页采购、一页销售、一页盘点，含加载、空态、禁用、弹窗 |

## 13 不影响已有正常功能的变更规则

1. 修改前读取当前文件与未提交差异，确认哪些代码属于已有正常功能或用户正在修改。不能覆盖、清理或格式化与任务无关的内容。
2. 先确定问题和最小修复范围；不要在修一个表单时重写全站状态、路由或后端架构。重构与行为变更尽量分步，公共接口确需变更时同步全部调用方。
3. 保持已验证接口、状态编码、响应字段与数据语义兼容；删除旧路径/字段前确认无调用和必要数据已迁移。不能以“统一风格”为由改坏已用接口。
4. 对高风险修复先建立回归场景，再改实现；修复后跑受影响测试及第12.4节最低回归。测试通过后不反复运行无关全量检查浪费时间。
5. 发现已有失败时区分基线问题与本次引入问题，写清实际结果；不能修改断言、禁用测试或标绿掩盖。
6. 禁止通过硬编码成功、删除历史数据、跳过事务、放开鉴权、清空缓存/数据库来让演示暂时通过。
7. 交付说明写清改了什么、为何、验证了什么、未验证什么；仅代码生成或编译通过不能说“全部功能正常”。

## 14 开发效率与质量门禁

### 14.1 首次脚手架应一次建立

统一布局、主题、路由守卫、认证Store、请求实例、错误反馈、状态字典、分页模型、金额/日期/资源路径工具，以及后端响应、异常、当前用户、权限组件、分页和统一Clock。随后通过一个简单档案功能验证端到端模板，再复用模板推进业务。

数据库Mapper生成只辅助基础字段映射，生成后必须核对生成列、JSON、可空字段、金额、外键和权限。禁止批量生成页面后未联调就标记完成；不要为提速省略审核、对账、盘点或AI降级。

### 14.2 统一命令入口

以下为脚手架需要提供的目标命令，目前不代表命令已经存在或已执行。根README列出实际运行目录和环境变量。

# frontend目录

格式、类型、受影响测试和构建失败时不标记完成；依赖不可用或外部API无法验证时明确保持对应项未验证。性能优化基于实际慢查询/交互证据，不先堆缓存和架构。

### 14.3 配置、仓库和提交

环境变量或未提交本地配置保存数据库口令、JWT密钥、模型密钥、文件目录；提交不含秘密的示例配置。前端任何`VITE_*`变量都按会被浏览器读取处理，不放密钥。不得为了便于启动将已知root口令写入代码。

## 17 开发者每次开始与结束的执行清单

**交付前：** 核对未扩大业务 → 检查权限、事务和输入输出 → 执行对应测试及最低回归 → 同步权威需求、唯一SQL与必要运行说明 → 如实标记验证状态 → 报告实际完成和未验证项。

任何实现若需要通过破坏已验证流程、降低权限隔离、覆盖历史或制造假成功来提速，均不符合本规范。
